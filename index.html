1인 제품 사업자를 위한 Orca 팀 운영

모바일 운영편 · 2026-10-19 · 오늘의 업무에 맞는 운영 방식 선택

사용자가 확인한 목표: 혼자 앱·서비스·게임·웹을 만들며 리서치·기획·디자인·개발·QA 전체를 담당한다. 이 자료는 그 전 과정을 에이전트와 운영하는 방법을 다룬다. 구체적인 첫 제품·고객·예산·출시 일정은 아직 정하지 않았으므로 예시는 운영 제안이다.

내 회사의 기본 구조: 내가 제품 책임자, 에이전트는 역할 수행자

내가 맡을 것: 누구의 어떤 문제를 풀지, 이번 출시 범위, 돈과 시간이 들어가는 선택, 최종 채택과 공개. 조율 담당이 맡을 것: 작업을 작은 결과물로 나누고 선행 조건·담당·질문·검증을 연결하는 일. 작업자가 맡을 것: 정해진 범위 안에서 자료·기획·디자인·코드·검수 증거를 만드는 일. 역할 여섯 개가 항상 실행 중인 에이전트 여섯 명을 뜻하지 않는다.

역할을 나누는 기준은 다음 담당자가 받을 산출물

리서치 → 기획: 고객 문제·경쟁 대안·근거 링크·확인 못한 가정. 기획 → 디자인/개발: 사용자 흐름·범위·예외·합격 기준. 디자인 → 개발: 화면 상태·상호작용·문구·사용할 자료. 개발 → QA: 실행 방법·변경 범위·시험 조건·알려진 문제. QA → 나: 통과/실패/미검증과 재현 순서. 다음 담당자는 인계 내용을 짧게 되짚은 뒤 착수한다.

제품마다 먼저 확인할 가치가 다르다

웹: 핵심 행동 하나가 이해되고 끝까지 가능한가. 서비스: 사용자 흐름과 데이터·계정의 경계가 맞는가. 앱: 대상 기기에서 핵심 흐름·권한·화면 상태가 맞는가. 게임: 핵심 플레이 반복이 이해되고 재미의 가설을 시험할 수 있는가. 첫 단계부터 결제·회원·관리자·멀티플레이 등 모든 기능을 동시에 만들지 않는다. 이것은 범위 조절 제안이지 특정 기능을 금지하는 규칙이 아니다.

같은 회사의 공통 규칙과 제품별 맥락을 나눈다

공통 운영 메모에는 보고 형식·검수 원칙·외부 전송/출시 결정 규칙을 둔다. 제품별 메모에는 고객·목표·용어·결정 사항·현재 결과·다음 행동을 둔다. 오늘의 작업 요청에는 이번 산출물·수정 가능 범위·합격 기준만 넣는다. 에이전트가 필요한 메모를 읽고 요약하도록 해서 매번 긴 배경을 다시 쓰는 일을 줄인다. 파일이 있다는 이유로 모든 세션이 자동으로 읽었다고 가정하지 않는다.

한 제품의 기본 팀을 먼저 검증한다

시작은 조율 담당 하나와 실행자 하나로 한다. 조사가 필요하면 먼저 조사 역할을 수행하고, 기획이 정해진 뒤 구현을 시작한다. QA는 구현이 멈춘 후보를 독립적인 기준으로 확인한다. 독립 업무가 확인되면 그때 병렬 작업자를 늘린다. 여러 제품을 운영해도 각 제품의 현재 후보·미완료·다음 행동을 구분한다. 모든 제품의 작업자를 항상 켜놓을 필요는 없다.

먼저 판단: 지금 가이드가 나에게 도움이 되나?

기존 가이드는 조작 실수를 줄이는 준비 자료로는 쓸 수 있다. 하지만 무엇을 병렬화할지, 언제 팀을 쓰지 말아야 할지, 내 검수 시간을 어떻게 줄일지를 결정하기에는 부족했다. 이 운영편은 그 결정을 돕는다. 메뉴를 먼저 외우지 말고 오늘 끝낼 결과 하나를 아래 방식 중 하나에 연결한다.

효율의 기준은 에이전트 수가 아니라 채택 가능한 결과와 내 소요 시간이다. 내 지시 시간 + 질문 대응 + 검수 + 재작업을 합쳐 본다. 응답은 빨라졌는데 이 합계가 늘면 운영 방식이 개선된 게 아니다. 사용량도 실제 기록으로 비교한다.

1. 오늘의 일을 네 가지 방식 중 하나로 고른다

작은 수정 → 한 명에게 끝까지

예약 안내 문구 수정, 한 화면 오류 수정처럼 목표가 명확하고 짧은 일. 같은 공간에서 한 에이전트에게 맡기고 내가 결과를 본다. 조율자·검수자를 무조건 추가하지 않는다. 역할을 늘리는 설명 시간이 구현 시간보다 커질 수 있다.

정답이 불분명한 중요한 결정 → 두 안 비교

첫 화면 구성이나 핵심 기능 접근법처럼 대안을 비교할 가치가 클 때. 같은 입력·같은 기준으로 Claude/Codex에 독립적으로 맡긴다. 문서 제안만 비교하면 작업 폴더까지 분리할 필요가 없을 수 있다. 동시에 코드를 수정한다면 분리된 작업 공간을 준비한다. 비교는 매번 하지 말고 틀린 선택의 비용이 큰 지점에 쓴다.

서로 기다릴 필요 없는 일 → 병렬 분담

예약 FAQ 초안과 외부 API 조사처럼 서로의 결과 없이 시작할 수 있는 일. 입력 자료와 결과 파일의 소유자를 분리하고 동시에 맡긴다. 조사→정책 결정→화면 구현처럼 앞 결과가 뒤의 입력이면 순차로 진행한다. “기획·디자인·프론트·백엔드”라는 역할 이름만으로 병렬 작업이 되는 것은 아니다.

질문과 인계가 많은 일 → 감독형 조율

여러 작업자가 질문하고 결과를 돌려보내며 선행 작업을 기다려야 할 때. 조율 담당 하나가 Orca 기능으로 배정·질문·완료를 추적한다. 나는 모든 작업자 창을 돌기보다 조율 담당에게 결정과 결과 요약을 받는다. 다만 조율 담당이 실제 메시지를 처리하는지 첫 작은 작업에서 확인해야 한다.

선택 흐름: 한 명으로 끝낼 수 있나? → 그렇다면 단독. 대안을 비교할 가치가 큰가? → 독립 비교. 결과 파일과 선행 조건이 분리되는가? → 병렬. 질문·의존 관계·인계 추적이 필요한가? → 감독형 조율. 이는 작성자의 운영 제안이다.

2. Orca의 기능을 내 시간 절약에 연결한다

아래는 Orca에서 묶어 쓸 수 있는 기능의 실용적 활용이다. 다른 제품에는 없다고 주장하는 목록은 아니다. 기능은 공식 자료로 확인했지만 이 사용자의 설치 환경에서 실행 검증하지 않았다.

워크트리 + 여러 에이전트: 실험 때문에 원래 작업을 잃지 않기

쓸 때: 같은 제품의 A/B 구현을 비교하거나 독립 기능을 동시에 수정할 때. 같은 출발점을 지정해 별도 파일 공간에서 진행하고 한 후보를 채택한다. 폴더 분리는 계정·DB·포트의 분리를 보장하지 않으므로 환경 준비는 담당자에게 확인시킨다. 쓰지 않아도 될 때: 한 문구 수정, 같은 후보의 순차 검수.

공식 근거: 공식 근거 열기

Design Mode: “여기 이 버튼”을 길게 설명하지 않기

쓸 때: 화면의 간격·문구·버튼 위치가 마음에 들지 않을 때. 공식 절차는 Orca 브라우저에서 페이지 열기 → 툴바 Design Mode 켜기 → 해당 요소 클릭 → 연결된 에이전트 대화에서 원하는 변경 입력이다. 요소의 화면·HTML·스타일 정보를 전달해 설명할 대상을 구체화한다. 실제 메뉴 위치와 전달 대상은 현재 화면에서 확인한다.

보낼 말: “선택한 예약 버튼을 모바일에서 한 줄 전체 너비로 바꾸고 아래 안내와 간격을 늘려주세요. 제출 기능과 다른 버튼은 유지하세요. 수정 후 같은 화면을 보여주세요.” 성공은 기능을 실행했다는 보고가 아니라 같은 화면을 다시 봤을 때 요구가 충족되는 것이다. 소스 줄 연결은 개발 환경 정보가 있을 때의 조건부 기능이다.

공식 근거: 공식 근거 열기

Diff 주석: 수정 의견을 한 번에 묶어 전달하기

쓸 때: 변경된 문구·설정·코드 중 정확한 부분을 지적할 때. 공식 절차는 diff의 해당 줄 옆 + → 의견 작성 → Send to agent → 수신 에이전트 선택이다. 이해 가능한 부분에만 주석을 남긴다. 모르는 코드는 읽기 전용 검수자에게 설명받는다. 화면 모양 문제는 Design Mode가 더 직접적이다.

운영 팁: 사소한 의견 하나마다 구현을 중단시키지 말고 한 차례 검토 후 묶어서 보낸다. 잘못된 범위 수정이나 데이터 문제가 보이면 즉시 중단시킨다. “디자인이 별로” 대신 “이 문구를 바꾸고 이 동작은 유지”처럼 수정과 보존 조건을 함께 준다.

공식 근거: 공식 근거 열기

오케스트레이션 스킬: 질문을 내가 직접 배달하지 않기

Opus 또는 Astra는 조율 담당의 판단을 만드는 모델이고, Orca 스킬은 그 담당자가 작업 배정·메시지·완료 추적 기능을 사용하는 안내다. “팀을 만들어줘”만으로 어떤 실행 방식인지 확정되지 않는다. Orca 기능을 사용할지 명시한다. 작업 등록만으로 자동 실행되거나 검수가 끝나는 것은 아니다.

보낼 말: “새 도구를 개발하지 말고 현재 Orca orchestration 안내에 따라 감독하세요. 실제 작업자와 작업 공간을 알려주고, 내 결정이 필요한 질문만 모으세요. 전달·수신·완료를 구분하고, 완료 보고 뒤 검수 결과를 보여주세요. 지원되지 않으면 만들어졌다고 말하지 마세요.”

공식 근거: 공식 근거 열기

워크스페이스 보드: 다음에 내가 볼 일을 고르기

사용자 사진의 보드는 Todo·In progress·In review·Done이다. 역할 인원표보다 결과물 진행판으로 쓰는 것을 권한다. 예: “예약화면-A”, “예약화면-B”, “취소안내 적용”. 역할이 여럿이어도 같은 공간에서 순차 작업한다면 카드가 역할 수만큼 필요하지 않다.

내가 돌아왔을 때의 순서: 조율 담당에게 결정 대기 질문 요청 → In review의 제출 결과 확인 → 진행 중 막힘 확인 → 여력이 있을 때만 Todo 착수. 이 순서는 운영 제안이다. 보드 Done이 검수·백업·배포·프로세스 종료를 대신하지 않는다. 현재 카드 상태 전환 동작은 이 문서에서 실행 검증하지 않았다.

3. 예약 서비스를 만든다면 이렇게 하루를 운영한다

예시 목표: “오늘은 예약 시연 화면을 직접 눌러볼 수 있게 만들고, 실제 예약 시스템은 만들지 않는다.” 납품 범위를 작게 잡으면 내가 확인할 방법도 분명해진다.

시작 — 조율 담당에게 목표·허용 범위·수락 기준을 준다. 현재 파일과 미완료 상태를 먼저 요약하게 한다. 세션을 바꿀 때마다 기획을 처음부터 설명하지 않도록 목표·결정·현재 결과·다음 행동이 든 짧은 작업 메모를 유지한다. 자동으로 모든 세션이 읽는다고 가정하지 않고 읽었다는 요약을 확인한다.

설계 — 예약 입력 항목과 오류 기준을 확정한다. 아직 모르는 정책은 질문으로 남긴다. 화면 구현과 서버 작업이 같은 인터페이스에 의존하면 그 합의부터 한다. 이번 시연에는 서버 작업자를 만들지 않는다.

실행 — 첫 안은 한 작업자가 만든다. 접근법을 비교할 가치가 큰 경우에만 A/B를 요청한다. 자료 조사처럼 독립 작업이 있다면 결과 파일을 분리해 함께 진행한다.

검수 — 화면을 직접 누른다. 문구·간격은 구체 위치를 선택해 전달한다. 외부 통신·파일 범위·데이터 처리는 검수자에게 근거를 받는다. 결과를 만든 사람의 “완료”만으로 채택하지 않는다.

종료 — 채택한 후보 하나를 보존한다. 원격 백업·배포는 별도로 결정한다. 조율 담당에게 남은 프로세스, 질문, 다음 행동 하나를 보고받는다. 다음 날 그 메모와 실제 파일 상태를 대조하고 이어간다.

4. 업무가 개발이 아닐 때도 팀을 써야 하나?

조사·기획·문서·콘텐츠 제작은 결과의 성격이 다르다. 동시에 같은 파일을 수정하지 않는다면 Git 워크트리를 반드시 만들 필요는 없다. 조사자는 출처·사실·추정을 구분해 보고하고, 작성자는 확정 자료로 초안을 만들며, 검수자는 근거와 독자 관점으로 확인한다. 도구를 늘리기보다 인계할 산출물을 명확히 한다.

예: 경쟁 서비스 조사 → 내가 고객·차별점 결정 → 랜딩 문구 작성 → 근거와 표현 검수. 경쟁 조사와 고객 문의 정리는 병렬 가능하지만, 차별점이 확정되기 전에 완성형 랜딩을 여러 명에게 만들게 하면 버릴 결과가 늘 수 있다. 이는 일반 예시이며 실제 사용자의 사업 분야를 확인한 것은 아니다.

5. 대장 모델은 무엇으로 고르나?

처음에는 이미 로그인·권한·Orca 연결이 확인된 모델 하나로 기준을 만든다. 놓친 질문, 범위 이탈, 재작업, 내 개입 시간으로 평가한다. 문제가 구현 품질이면 대장을 바꾸기 전에 작업자 입력과 검수 기준을 확인한다. 조율 실패가 반복될 때 같은 작은 과제를 다른 대장 후보로 비교한다.

Astra·Opus·Fable 중 사용자 업무에 가장 효율적인 후보는 아직 검증하지 않았다. 큰 모델이 언제나 더 나은 팀장이거나, 도구가 특정 역할에 고정된다고 가정하지 않는다. 모델 가용성과 사용량은 실제 계정에서 확인한다.

6. 오늘 밖에서 결정할 것은 세 가지뿐

첫째, 세팅 후 끝낼 첫 결과 하나. “서비스 완성” 대신 “예약 시연에서 입력·오류·요약 확인” 정도로 구체화한다. 둘째, 내 확인 기준 세 가지. 셋째, 단독·비교·병렬·감독형 중 어떤 운영 방식이 필요한지. 이 세 가지를 정하면 돌아와서 메뉴를 따라가는 목적이 생긴다.

현재 맥의 file:// 주소와 localhost는 외부 휴대폰에서 같은 자료를 여는 주소가 아니다. 이 읽기 자료는 GitHub Pages용 웹 문서로 준비했다. 게시가 확인된 HTTPS 주소로 휴대폰에서 연다. Orca 모바일 앱으로 실제 작업을 관리하는 것은 별도의 연결·준비 과제이며, 문서를 읽는 데 필요하지 않다.

밖에서도 일이 이어지는 하루 운영법

운영 제안: 모바일의 목적은 작은 화면에서 모든 일을 하는 것이 아니라, 내 결정을 기다리는 작업의 대기 시간을 줄이는 것입니다.

1. 처음 한 번: 휴대폰을 내 데스크톱과 연결

공식 문서 기준으로 데스크톱의 계정/상태 메뉴에서 일회용 연결 코드를 만들고, 모바일 앱의 Pair에서 입력합니다. Relay는 로그인이 필요하며, 직접/LAN 연결은 데스크톱 주소에 도달할 수 있어야 합니다. 모바일은 데스크톱의 원격 제어 화면입니다. 데스크톱 연결이 끊겨도 휴대폰이 대신 작업을 수행한다고 생각하면 안 됩니다.

공식 문서 확인: Orca Mobile · 베타·버전 의존. 사용자 기기의 실제 연결과 외부망 접속은 미검증.

2. 외출 전: 조율 담당에게 이 문장을 전달

예약 서비스의 오늘 목표는 ‘예약 요청 화면을 검수 가능한 상태로 만들기’야.
업무별 담당과 수정 범위를 먼저 정리하고, 서로 기다려야 하는 순서를 확인해.
작업마다 완료 증거와 검수할 위치를 남겨. 판단이 필요하면 질문 하나에 선택지와 추천 이유를 붙여.
배포·결제·데이터 삭제는 이번 범위에 포함하지 않아.
내가 외출 중이어도 연결 문제나 승인 대기를 완료로 보고하지 마.

나가기 전에 휴대폰에서 정확한 호스트·프로젝트·세션을 열고 테스트 질문에 답해 봅니다. 데스크톱이 연결 가능한 상태인지 확인합니다. 절전 중 지속 실행은 이 가이드에서 검증하지 않았습니다.

3. 외출 중: ‘진행해’ 대신 범위를 답하기

질문 앞뒤의 작업 상태를 읽고 “예약 화면 작업: A안으로 진행. 결제 기능은 제외. 완료 후 화면과 미해결 사항을 남겨”처럼 답합니다. 공식 모바일 기능에는 세션 확인과 프롬프트 응답이 포함됩니다. 실제 변경 화면과 전체 동작 검수는 복귀 후 진행하는 운영을 권합니다.

열 이름과 워크스페이스 카드는 제공 화면에서 확인했습니다. 위 이동 기준은 작성자의 운영 제안입니다. 보드는 직원 명단이 아니라 작업 공간의 상태를 보는 데 사용하세요. 열 이동만으로 에이전트 실행·중단·검수 통과가 자동 처리된다고 단정하지 않습니다. 현재 버전의 이동 조작과 자동 상태 연동은 추가 확인 대상입니다.

효율 기준: 동시에 맡긴 수보다 ‘내 검수를 통과한 결과 수’를 보세요. 처음에는 진행 작업 1~2개로 시작하고, 질문 대기와 재작업이 쌓이면 새 작업을 늘리기보다 기존 결과를 정리하세요. 이는 성능 측정값이 아닌 운영 권장안입니다.
